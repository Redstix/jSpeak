## 结论

1. **内部文件二进制 I/O 可用**：64KiB 的 `.bin` 与 64044 字节的 `.wav` 都成功写入并全字节读回。
2. **运行时音频出口已完整验证（含实际出声）**：JS 生成 → 内部 WAV → 字节验证 → audio 播放 → ENDED，用户确认听到低音—停顿—高音、顺序正确。
3. **不能把包内读取失败归因于 `.bin` 扩展名**：相同文件 API 读包内 bin/dat/wav 都失败，读内部 bin/wav 成功。交付后本地核查 RPK：`common/probe.bin`、`probe.dat`、`tone.wav` 确在包内；且同一 `/common/tone.wav` 可被 `@system.audio` src 播放（0.1.0 听感确认）。故 202 并非文件缺失或路径大小写问题，而是 file API 对包内路径的读取限制。不能因此宣称所有资源 API 都不可用。
4. **第一版 381ms gap 不足以代表持续调度性能**：本轮首等待158ms、后续max9ms，提示启动等待与后续调度应继续分开，但不证明上轮381ms一定是首次等待。
5. **尚未证明 eSpeak JS 实时性能**：双音是简单正弦，不是 eSpeak DSP。77ms 最大片值得关注，不应拿 534ms / 2s 推导项目已能实时合成。
6. **仍未证实原始 PCM streaming、连续文件无缝播放、长文本内存上限、完整取消/前后台和多轮稳定性**。

## 后续建议（尚未实施）

- 不再尝试更换资源扩展名（已排除）。核验 `@system.file` readArrayBuffer 支持的 URI 前缀与包内路径支持；调查替代包内二进制读取途径。注意：把包内资源“复制到 internal”本身仍需一种包内读取途径，先确认可行再投入。
- 若包内复制/读取都受限，再比较构建期生成 JS 数据模块的可行性，必须测包体、启动峰值内存和解析耗时；不能默认它适合大型词典。
