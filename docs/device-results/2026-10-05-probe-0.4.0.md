各模式终态：

- assemble：`PASS; verifiedResident=898009B; buffers released`。每个文件按页读入并复制到完整数组，全部页及组装文件 hash 校验后同时保留，完成后释放应用引用。

当前候选集共 **898009 字节**；仍标记 `closureComplete:false`。已知动态语言切换依赖及其他未核验资源没有因此自动闭合；详见 [DATA_PACK](../DATA_PACK.md)。

设备使用 seed 0 的 signed-int32 xorshift 字节 hash，**不是设备端 SHA256**。桌面/RPK 中原始数据的长度与 SHA256 已独立核验；设备此次返回的长度和 hash32 均符合该构建的固定预期。

## D1 分页、窗口与 EOF

固定页大小为 **32768 字节**。scan 报告 `en_dict` 为 **6 页、182152 字节**，`phondata` 为 **19 页、600104 字节**，均 PASS。按照冻结探针逻辑，只有每页长度/hash 校验通过且覆盖到文件末尾才输出该汇总；屏幕没有逐页打印所有 hash。

## 计时行的归属及含义

0.4.0 页面对 `D1 本轮`、`D1 身份`、`D1 计量` 使用共享结果键，并按原来位置覆盖。各模式的逐文件行则保留。冻结 RPK 内代码已直接核对，确实是 `result('D1 计量', metrics())`；当前修复中的源码不能倒用于解释旧构建。

因此，OCR 中挨着 whole 行的共享计量 **不是 whole 的计量**。其 `assemble=37ms` 只能来自 assemble 分支，且 `livePeak=930777B` 恰等于候选集 898009 加一个 32768 字节临时页；应归属 **assemble**。

`D1 本轮 #4` 是所有 D1 模式累计启动计数，不是 whole 第 4 次。四种模式的 PASS 与按按钮顺序完成四次运行相容，但共享字段没有独立 run ID；不据此证明具体启动顺序、冷/热状态，或把重复 OCR 图片算作重复测试。顶部 `STOPPED` 也不撤销此前完成且保留下来的 PASS 行。

`19764 - 2308 - 14344 - 37 = 3075ms` 是上述局部计时未覆盖的差额，可包含 10ms defer、UI 更新、调度及其他工作，不能算作额外纯 I/O 或复制成本。

**685ms 是需要保留和调查的异常。** 正常时钟条件下，分配/复制累计仅 37ms，因此该峰值来自某个 hash 代码块；hash 每片最多 4096 字节。计时可能包含 GC/抢占等影响，它既不是完整应用最大阻塞测量，也不是 eSpeak DSP/RTF。whole 与 resident 的 phondata hash 时长不同，不能在缺乏冷/热及环境控制的情况下直接解读为性能退化。

`livePeak` 统计 retained backing stores、当前读取 backing store 和组装数组；**不包含所有 JS 对象、manifest、引擎、模块解析、GC 尚未回收对象或原生桥接副本**。`buffers released` 只证明探针清除了应用引用，不证明 GC 当场归还内存。本轮没有寻找设备内存上限，也没有测完整词典/音素 reader 初始化峰值。

## A1 增量写入失败的证据边界

append 与 position 均显示 `PASS header overwrite; writes=5`，但随后长度校验失败。该 PASS 仅表示写 API 成功回调，**不证明头回填语义正确**；最终失败正确阻止了播放。两条失败路径都显示 `PASS removed owned file`。

对原实现的 `source.subarray(...)` 写入视图进行桌面精确模拟：若原生写入实际消费完整 backing ArrayBuffer 的 46424 字节，长度可复现为：

- append：独立的 44 字节 provisional header，加三次源 backing buffer，`44 + 3 × 46424 = 139316`。
- position：最后一个 PCM 分块起点为 32812；若写入完整源 backing buffer，末尾为 `32812 + 46424 = 79236`。

两项与设备读回长度完全相同，**强烈支持视图长度在写入边界丢失的解释**。但设备未导出失败文件的逐字节内容，不能据长度进一步断定 byteOffset 是否也被忽略，或确定原生实现细节。尤其不能把这次失败升级为“append/非零 position/头回填 API 不支持”。

0.4.1 修复方向是在每次写入前提供与目标字节片段等长的独立 backing buffer，并继续进行完整读回检查。该修正版的本地测试和构建属于另一份交付证据；**按钮 9/10 的增量写入能力目前仍待修正版真机确认**。当前已证可用的文件消费方案是有上限的短句完整 WAV 写入与播放。

## 可以升级和仍不能升级的结论

本轮可记录为已实测通过：这份固定候选集的两大文件全读、32KiB 顺序分页、跨页/高偏移/末尾窗口、精确 EOF 空返回、6 文件整读驻留与组装驻留；固定 22050Hz 参考语音经包内路径及完整 WAV 文件路径实际出声。

仍未确认：完整 en-us 依赖闭包、核心数据解析/初始化、设备内存或存储上限、真实 heap 峰值、受控冷/热性能、完整应用阻塞上限、取消延迟与多轮资源增长、增量写入修正版、长文本/连续播放以及 JS DSP 实时能力。685ms hash 切片异常保持待调查，不用本轮“能读入和能出声”覆盖性能问题。
