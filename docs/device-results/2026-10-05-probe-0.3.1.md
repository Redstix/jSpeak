## 分析

1. **内容嗅探不存在**（C1）：.txt 名 + 纯二进制内容（与 probe.bin 逐字节相同）读取成功且逐字节 hash 一致。"invalid file type" 校验**仅基于文件名（扩展名）**，与内容无关。装载策略不再有任何编码开销。
2. **尺度成立**（C2）：256KiB 一次性 readArrayBuffer + 设备端 hash 校验通过，读+hash 2048ms。与 C1（64KiB/454ms）近似线性，为真实词典装载的启动耗时提供了量级依据（含 hash 校验成本；纯读取耗时更低）。
3. **包内路径支持 position/length**（C3）：直接对 `/common/bin.txt` 做切片读，hash 与预期一致——**词典无需整读驻留内存，也无需复制到 internal，可直接分页随机访问包内数据**。
4. **copy→internal 出口关闭**（C4+C5）：对 .txt 与 .bin 包内源一律原生 `InternalError: invalid parameter`（同步抛出，经 JS 包装捕获）。构建身份已确认（本轮行结构为 0.3.1 独有，`dstUri` 参数名正确），排除了 0.3.0 B4 的"缺参"解释。**0.3.0 B4 歧义就此消解——无论当时安装的是哪个构建，结论相同。** 官方契约（copy srcUri 无资源路径限制）与设备实现的差异记录在案。
5. **access 对包内路径关闭**（C6）：与文件类型无关，一律 `invalid parameter :path`。对装载无影响（文件存在性可由 read 成败推断）。
6. **探针侧措辞瑕疵（非设备发现）**：copy 失败后清理子行对**从未创建**的目标文件发 delete，返回 301，显示为 "FAIL ... leftover: <uri>"——301 恰恰证明无残留，措辞误导。后续探针版本应把"copy 失败后清理遇 301"表述为"无需清理（文件未创建）"。本轮无需修复（copy 出口已关闭，不再有 copy 行）。
7. **生命周期**：整节 DONE，无看门狗触发；C 行总耗时约 2.9s（阈值 35s）。

## 装载方案定案（决策树终态）

**出口：包内 .txt 直读。**

- eSpeak 数据文件（词典、音素表等）**内容保持二进制原样，仅文件名使用 .txt 扩展**打包进 RPK。
- 装载：小文件 readArrayBuffer 全量读入内存；大词典用 `position/length` 分页随机访问（C3 已证原语可用）。
- 不需要 base64/文本编码（C1 排除内容嗅探）；不需要 copy→internal 缓存（C4/C5 关闭）；`internal://files` 保留给运行期产物（WAV 等，0.2.0 已证）。
- 已证边界：单文件 ≤256KiB、64KiB/256KiB 全量读、2KiB 切片读。
- **留待真实数据轮验证**：>256KiB 尺度、真实数据规模下的启动耗时与峰值内存、接受的扩展名全集（只有 .txt 被证明，其他类型无必要）。
