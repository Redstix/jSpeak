## 可以得出的结论

- 本次被测 JS 数值/TypedArray/DataView 语义通过，64 KiB 分配可用；不是完整 ECMAScript 兼容认证或 heap 上限。
- 包内测试 WAV 的播放路径已由音频结束事件和人工听觉共同确认。
- 当前 `/common/probe.bin` + `file.readArrayBuffer` 组合失败，需要调查数据访问路径。
- 设备 API 虽有返回，但 `ap / 0.0.0` 不足以识别硬件或固件；不要把它当作真实固件版本。

## 不应推断的结论

- 未证明运行时生成 WAV、写文件后播放、原始 PCM 流式写入、连续小文件无缝播放。
- `invalid file type` 不能直接归因于 `.bin` 扩展名、签名、权限或二进制读取整体不支持。需要对照路径与 API。
- 791ms 包含主动定时等待，不是纯计算用时；不能除以某个音频时长当作 RTF。
- `gap=381ms` 是包括第一次启动等待在内的单次最大间隔，没有样本分布；可能涉及启动/调度等因素，当前不能断言 GC 或持续卡顿。
- 未单独确认取消音频、前后台切换、重复三次的行为。

## 下一轮验证重点

1. 同一数据不同扩展名（如 `.bin` 与 `.dat`）、已知可播放 WAV 的 binary read，分离资源类型问题。
2. 依据官方 API，验证应用内部可写路径的字节写入/读回，保留各步错误。
3. 用设备 JS 生成小型 PCM16 WAV，写入后播放：确认运行期音频出口，而不只播放预置资源。
4. 计算计时分离首调度延迟、各片纯计算时间、后续调度间隔，做短小的重复测量。
