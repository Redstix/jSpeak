## 分析

1. **包内资源路径可被 file API 读取，门槛是文件类型**：同一 API、同一会话——`.txt` PASS（readText 与 readArrayBuffer 双通过，512B，文本/字节 hash 均与本地一致），`.bin/.dat/.wav` FAIL `202 invalid file type`（0.2.0 三类 + B6 大写复证）。"invalid file type" 字面成立：校验基于文件（扩展）名，而非"资源路径一律拒绝"。
2. **修正 0.2.0 的 C+ 推断**：不是 readArrayBuffer 的资源后端整体缺失，而是类型校验集合与官方契约的差异。官方契约（支持资源路径）在设备上对被接受类型成立。
3. **B3 access FAIL `invalid parameter :path`**：access 对包内路径的原生参数映射失败——错误形态与 readArrayBuffer 的回调式 202 不同，按 API 各异，不能在 file API 成员间外推。
4. **B4 copy FAIL（.bin 源）**：file.copy 同步抛出原生错误（经 JS 包装捕获，code=JS）。由于上述构建身份歧义 + 源是被拒类型（.bin），不能据此关闭"copy→internal"出口——若类型校验同样作用于 copy 的源，`.txt` 源的复制仍可能可行。0.3.1 C4（.txt 源）/C5（.bin 源，带构建戳）分别判定。
5. **B7 internal 部分读 PASS**：`position/length` 随机访问在 internal 分区成立——词典分页读取的原语就绪。64KiB 全链（get 检查+写入+全量读+部分读）1807ms，作为后续大文件操作的基线参考。
6. **清理契约与生命周期**：6 个 file API 行 + B7 链后清理 PASS，取消/清理机制在 0.3.0 结构下仍然成立。

## 装载方案修正

0.2.0 的候选出口更新为：

- **新首选（待 0.3.1 确认）——"文本扩展名直读"**：数据字节不变，仅文件名使用 file API 接受的类型（.txt 等），运行期 readArrayBuffer 直接读包内资源，无复制、无编码开销。待证前提：a) 校验只看扩展名不看内容（本轮 .txt 是真 ASCII，未测 .txt 名+二进制内容）；b) 尺度可行（只证 512B，未测数百 KB）；c) 包内路径是否支持 position/length（决定可否不整读驻留）。
- **copy→internal 出口仍开放**：C4/C5 判定。
- **文本编码（base64 等）**：仅在内容嗅探存在时作为退路；构建期 JS 数据模块仍是最后手段。

0.3.1「装载判别」矩阵：C1 包内 .txt 名二进制 64KiB 直读（内容嗅探 vs 扩展名）；C2 .txt 名二进制 256KiB（尺度）；C3 包内路径部分读；C4 copy(.txt 源)→internal 读回；C5 copy(.bin 源) 复测（构建戳消歧）；C6 access(.txt)。
